# 整理与留底工具（housekeeping）

本目录管的是**工作区卫生**：把散落的临时件先留底、再清理，并且**留得可查、删得有据**。

工具是踩出来的，不是设计出来的。第四轮（0.4.12）整理时踩了两个真实事故，规则表就是它们的墓碑。

## 两次事故

### 事故一：留底包被原地覆盖（第四轮）

`_clean54.py` 被重复执行，留底包名固定 ⇒ 第二次执行把第一次的包覆盖，46 个条目彻底丢失，事后无法追溯删了什么。

### 事故二：清理孤儿依赖（本轮收尾）

清掉工作区散件 `_bak_0411.user.js` 后，验收脚本 `_verify54.js` 立刻 `ENOENT` 崩掉——**回归能力凭空消失**，而且要到下一次跑验收才暴露。

同一类缺陷在仓库里还有第二例：`docs/tools/release/_gitverify.py` 把路径写死在临时工作区。它之所以被发现，是因为按规则 5 做了一次机械扫描。

**教训**：删得掉的是散件，删不掉的是散件承载的凭据。要么把该文件**升格为仓库正式资产**（本轮 0.4.11 快照就是从散件升格为 `docs/versions/v0.4.11.user.js`），要么改掉引用它的脚本路径。二者必居其一。

## 六条硬规则

| # | 规则 | 对应事故 |
|---|---|---|
| 1 | **留底包名带唯一时间戳后缀**，永不原地覆盖 | 事故一 |
| 2 | **清单先落盘，再执行删除** | 崩溃时清单没写，事后无法追溯 |
| 3 | **删除逐项记账**（`journal.json`），支持断点续跑 | 中途崩溃后无法判断哪些已删 |
| 4 | **幂等判据是 `(文件名, sha256)`，不是文件名，更不是 ledger** | 见下方"三个坑" |
| 5 | **删前查依赖**：`--refscan` 扫仓库，命中即拒绝删除（`--allow` 可显式放行并记账） | 事故二 |
| 6 | **归档目录不参与引用扫描** | ledger/journal 里天然写满被归档的文件名，不排除就自己引用自己，永远拦截 |

### 规则 4 背后的三个坑

1. **不能用 `ledger.entries` 判重**。ledger 只证明"曾经尝试归档"，且它在打包**之前**落盘。进程若在"写台账"与"删文件"之间中断，文件会留在盘上却被判为已完成 ⇒ 永远清不掉。本轮真实发生过：台账记 32 条"已归档"，盘上 31 个文件还在，`journal` 只记 1 条删除。
2. **不能用文件名单独判重**。删掉之后又被重新创建的同名文件（内容已变）会被永久跳过，悄悄堆在工作区里。本轮收尾日志就撞上了。
3. **修复已发生的断裂要用 `--finish`**：只处理"台账已记但文件仍在盘"的条目，**先在归档包内按名找到并核对 sha256**，一致才删，不重新打包（避免 8MB 级重复留底）。

## 用法

```bash
# 干跑：只列计划，不改盘
python _housekeeping.py --ws <工作区> --archive <归档目录>

# 执行
python _housekeeping.py --ws <工作区> --archive <归档目录> --apply

# 带依赖扫描（规则 5，建议总是带上）
python _housekeeping.py --ws <工作区> --archive <归档目录> --refscan <仓库根>

# 显式放行被拦截项（记入 ledger 的 overridden 段，不是静默通过）
python _housekeeping.py ... --refscan <仓库根> --allow a.txt,b.txt

# 补删中断残留（规则 4 坑 3）
python _housekeeping.py --ws <工作区> --archive <归档目录> --finish --apply
```

退出码：`0` = 干净；`2` = 有需人工处置的项（被依赖文件，或补删时核对不通过）。

`--refscan` 按**文件名**做全文匹配，宁可误报不可漏报（fail-closed）。误报用 `--allow` 逐个放行，放行的名字与命中次数都记进清单，事后可复盘。

## 配套核对脚本

清理的最后一步不该是"我觉得清干净了"。两个脚本把这句话变成可复核的凭据：

| 脚本 | 作用 | 产出 |
|---|---|---|
| `_zipcov.py` | **留底包覆盖核对**：ledger 每一条都能在某个归档包里找到，且 sha256 逐字节一致 | `docs/reports/_zipcov.txt` |
| `_vault.py` | **收尾现状核对**：工作区是否真清空、关键资产是否齐全、台账是否自洽 | `docs/reports/_vaultout.txt` |

```bash
python docs/tools/housekeeping/_zipcov.py
python docs/tools/housekeeping/_vault.py <工作区1> [工作区2 ...]
```

两者都用"逐名 + 逐字节"而不是"看起来像"，因为清理事故有两种形态，必须分别排除：

- **删了但没留底** ⇒ 数据真丢（`_zipcov.py` 排这个）
- **留底了但没删** ⇒ 垃圾堆积且欺骗台账（`_vault.py` 的台账自洽段排这个）

## 与发布链路的关系

`docs/tools/release/` 负责**发布**（打包 / 校验 / 版本链 / 版本库层行尾）；本目录只负责**工作区卫生**（留底 / 清理 / 现状核对）。两者都产出可复核报告，落在 `docs/reports/`。
